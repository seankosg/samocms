# 발주처 업역과 네트워크 공정표 연계 검토 + 선행 영향 표시

업로드한 `★SAMO_통합공정표_20260915_발주처_취합.xlsx`(1,096행) 실측 결과를 바탕으로 정리했습니다.

## 1. 파일에서 확인된 사실

- 업역 구분: 당사(HDEC) 941건 / HMMME 129건 / 발주처 26건 → 발주처 업역 합계 **155건**
  (현재 앱에는 26건만 등록되어 있습니다)
- 발주처 업역 부서: Paint 47, IT 41, HM 25, Security 22, Assembly 13, Glove 4, Body 2, MS 1
- 연결 관계: 발주처끼리 16건, **발주처 ↔ 당사 22건**, 당사끼리 나머지

즉 발주처 항목은 독립된 덩어리가 아니라 당사 인허가 경로에 직접 물려 있습니다.

## 2. 선후행이 현재 네트워크 공정표에 주는 영향 (확인된 문제)

현재 네트워크는 선후행을 "번호 → 번호"로만 잇기 때문에 아래 경우 연결선이 **조용히 사라집니다**.

1. **건설 항목은 마일스톤 단위로 묶여 있음** — 건축·전기·기계·내장 항목은 개별 노드가 아니라 마일스톤 뭉치 하나로 표시됩니다. 그래서 발주처 R.33(GMS Cable Connection) → 당사 R.34(GMS/PRS 설치 완료, 기계) 같은 연결선이 화면에 나타나지 않습니다.
2. **번호가 아닌 말로 쓴 선행** — `건설 잔여작업`, `POP Submittal`, `FOP Submittal`, `설비 Comm.`, `발주처` 같은 표기는 잇지 못하고 경고 목록에도 뜨지 않습니다.
3. **다른 파일 번호 참조** — `E01`, `N04`, `R15(Chiller)` 등은 이 파일에 없는 번호라 끊깁니다.
4. 마일스톤 표기(`M.1` ↔ `M1`)는 이미 자동으로 맞춰지고 있어 문제가 없습니다.

## 3. 발주처 항목이 밀리면 당사 업역이 밀리는 경우 — 실제로 있습니다 (16건)

발주처 항목이 선행이고 당사 항목이 후행인 연결:

| 발주처(선행) | 당사(후행) | 영향 경로 |
| --- | --- | --- |
| R.5·R.6·R.7·R.9·R.10 (준공시험성적서·피난계획·최신승인도면) | R.26 POP DRIC 검사보고서 | → R.28 → R.30 → **M3 ECZA 부분승인** |
| R.13·R.14 (시설·소방 유지관리 계약서) | R.50 FOP 신청·인허가비 납입 | → **M6 ECZA 사용승인** |
| R.33 GMS Cable Connection | R.34 GMS/PRS 설치 완료 | → R.35 합동검사 → 가스공급 개시 |
| R.20·R.21·R.22 (FOP 시험성적서·피난계획) | R.56 Full HP 검사보고서 | → **M6** |
| R.48·R.49 (As-built Drawing) | R.66 As-built 취합 | → **M6** |
| R.69·R.70·R.72 (유지관리 계약서·자산목록) | R.73 최종검사보고서 | → **M7 / M8** |

한 줄 요약: **발주처 서류·시험 항목이 하루 밀리면 M3·M6·M7 인허가 마일스톤이 그대로 하루 밀립니다.** 지금 화면에는 이 파급이 전혀 표시되지 않습니다.

## 4. 어떤 방식이 나은가 — 결론

발주처 전용 네트워크를 따로 만드는 방식은 **권하지 않습니다.** 위 22건의 연결이 전부 화면 밖으로 사라져, 정작 중요한 "발주처가 밀리면 무엇이 밀리는가"를 볼 수 없게 됩니다.

권장안은 **기존 네트워크 하나를 유지하면서 발주처 업역을 그 위에 입히는 것**입니다. 대신 발주처 업역 섹션에서는 같은 네트워크를 발주처 중심으로 재배열해 보여 줍니다.

## 5. 만들 것

### (A) 네트워크 공정표 — 발주처 업역 입히기

- 발주처 노드에 전용 색(보라)과 `발주처` 라벨을 붙여 한눈에 구분
- 상단에 `발주처만` / `당사만` / `전체` 전환과 `발주처 연관만` 버튼 추가
- 발주처 ↔ 당사를 잇는 연결선은 굵게·강조색으로 그려 업역 경계를 드러냄
- 건설 뭉치에 물린 연결이 사라지지 않도록, 뭉치 안의 항목이 지목되면 그 뭉치 노드로 연결선을 잇고 라벨에 실제 항목 번호를 적음
- 번호가 아닌 말로 된 선행(`건설 잔여작업` 등)은 경고 목록에 모아 보여 줌

### (B) 발주처 업역 섹션 — 발주처 중심 보기

- `/owner/network` 페이지 추가, 가로 줄(레인)을 발주처 내부 부서(Paint·IT·Security·Assembly·HM)로 재배열
- 발주처에 물린 당사 선행·후행 항목은 회색 참고 노드로 한 단계까지 함께 표시해 흐름이 끊기지 않게 함

### (C) 선행 영향(밀림) 표시 — 제안

날짜가 바뀌면 화면에서 이렇게 보여 줍니다.

1. **원래 자리 남기기** — 노드는 시간축 위에서 종료일 위치에 놓이므로, 밀린 항목은 자연히 오른쪽으로 이동합니다. 이동 전 자리에 점선 유령 노드를 남기고 두 위치를 화살표로 이어 "여기서 여기로 밀렸다"를 그대로 보여 줍니다.
2. **며칠 밀렸는지 배지** — 노드 위에 `+3d` 형태로 표시하고, 선행 때문에 밀린 경우 `선행 영향 +3d`로 구분합니다.
3. **파급 경로 강조** — 밀린 발주처 노드를 누르면 그로 인해 밀리는 당사 후행들이 빨간 체인으로 이어져 마일스톤까지 불이 들어옵니다.
4. **영향 요약 줄** — 화면 상단에 "발주처 변경으로 당사 항목 N건, 마일스톤 M3·M6이 최대 x일 영향" 한 줄 요약.

밀림 판정 기준 두 가지를 함께 제공합니다.

- **실제 변경분**: 지난 업로드 기록과 오늘 값을 비교해 실제로 날짜가 바뀐 항목
- **예상 파급분**: 선행이 끝나야 후행이 시작한다는 규칙으로 계산한, 아직 일정표에 반영 안 된 밀림

## 6. 기술 메모

- `netNodes()`: 건설 롤업 노드에 구성 항목 번호 색인(`memberIds`)을 추가하고, `buildModel()`의 간선 해석에서 `byId` 미스 시 이 색인으로 롤업 노드에 매핑. 한글/문장형 참조는 별도 `softMiss` 목록으로 분리.
- 밀림 계산 모듈 신설(`src/lib/network-impact.ts`): 간선 그래프로 위상 정렬 후 전진 패스(`ES = max(선행 finish)+1`)로 `pushDays`와 파급 경로 산출. 실제 변경분은 `activity_snapshots`의 직전 스냅샷 `start_date`/`finish_date`와 비교.
- `layout()`은 종료일 기준 배치이므로 밀린 노드는 그대로 오른쪽으로 이동. 유령 노드는 이전 종료일로 좌표만 한 번 더 계산해 점선 렌더.
- `NetFilter`에 `scope: "all" | "owner" | "hdec" | "linked"` 추가, `nodeVisible()`에서 `isOwnerRow` 기준 판정.
- 발주처 중심 보기는 `netNodes`에 레인 기준 주입(부서 레인) 옵션을 더해 재사용.
- 파일의 발주처 155건 반영 여부는 업로드 화면에서 진행하며, 이 계획의 화면 기능은 26건 상태에서도 동작합니다.
